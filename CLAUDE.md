# Craftworks

A player-held crafting planner, the Personal Assembler. See `CONTEXT.md` for the domain glossary.

## Workflow

Commit on the current branch; open a feature branch only when the user asks for one.

Anything that changes the mod's behaviour gets a `/code-review`. Doc and plumbing changes skip it: that
covers `CLAUDE.md`, `CONTEXT.md`, ADRs, `docs/`, `.claude/` (skills, settings), submodule bumps, and
tooling or CI config.

## Releases

A change a player or pack author notices adds its line under `## Unreleased` in `CHANGELOG.md` as it lands. Before bumping `mod_version`, publishing to `~/.m2`, tagging a release or uploading to Modrinth or CurseForge, read `docs/agents/releases.md`: releases go through `scripts/release.sh`, which uploads last with `scripts/upload.py`, and a published version never changes, in `~/.m2` or on either site.

A release that must reach the Pack follows the `release-train` skill: one owning session per checkout, and pushes only on the user's word.

## Testing

`sh ./gradlew build` runs the JUnit tests (the Assembler's planning, with no Minecraft); `sh ./gradlew runGameTestServer` runs the game tests headless (a real player on a server) and names each one it ran. `python3 -m unittest discover scripts/tests` tests the upload step against a stand-in server on localhost. A new game test class is registered by a line in `CraftworksGameTests.registerTests`. A fluid machine's block models, and the Assemblers' rings (`assembler_connections`), are generated by `python3 scripts/build-machine-models.py`; a model past three blocks must be a composite, since Minecraft refuses an element beyond -16..32 and no headless run loads a model (`ModelBoundsTest` checks).

Neither run loads a client, EMI, JEI or Jade, so a change to their compat code, a screen, or a model or texture isn't done when the tests pass: list it for the user to check in the dev client, which they open (the `quicklaunch` skill, only at their word). The dev client loads `dev_pack/` (`craftworks:dev/with_fluid`, `craftworks:dev/two_fluids`, `craftworks:dev/two_results`) for the cases vanilla's recipes don't cover; add a recipe there when a change needs one to be seen. EMI builds its recipes on a loading thread of its own: nothing in a plugin's registration or a recipe's constructor may touch the font or `RenderSystem`, which only the render thread may, or EMI drops the whole plugin (as #33's text measuring did).
