# Craftworks

A player-held crafting planner, the Personal Assembler. See `GLOSSARY.md` for the domain glossary.

## Workflow

Commit on the current branch; open a feature branch only when the user asks for one.

Anything that changes the mod's behaviour gets a review by the `code-review` skill in `.claude/skills/` (mattpocock-skills:
a Standards and a Spec review, side by side), and by no other code review, Claude Code's built-in `/code-review`
included. Doc and plumbing changes skip it: that
covers `CLAUDE.md`, `GLOSSARY.md`, ADRs, `docs/`, `.claude/` (skills, settings), submodule bumps, and
tooling or CI config.

## Releases

A change a player or pack author notices adds its line under `## Unreleased` in `CHANGELOG.md` as it lands. Before bumping `mod_version`, publishing to `~/.m2`, tagging a release or uploading to Modrinth or CurseForge, read `docs/agents/releases.md`: releases go through the libworks plugin's `release` task, which uploads last with its `upload` task, and a published version never changes, in `~/.m2` or on either site.

A release that moves with Groundworks or Pipeworks follows the `release-train` skill: one owning session per checkout, and pushes only on the user's word.

## Testing

`sh ./gradlew build` runs the JUnit tests (the Assembler's planning, with no Minecraft); `sh ./gradlew runGameTestServer` runs the game tests headless (a real player on a server, with only Groundworks beside the Mod) and names each one it ran. Pipeworks, Jade and EMI or JEI are on the dev client only; `-PwithKubeJS` puts KubeJS on both runs `-PwithResearchd` puts Researchd on the dev client `-PwithAE2` puts AE2 there and `-PwithCurios` puts Curios and Dark Utilities there. The libworks plugin's `checkPlaysAlone`, which `build` runs, fails on another Module's id, namespace or required dependency in the Mod's code or resources, its generated vanilla pack included (libworks ADR 0005), `PlaysAloneTest` on a tag the code reads that the game tests don't check, and `PlaysAloneTests` on a tag the Mod's data names that only another mod fills (FactoryWorks ADR-0127). A new game test class is registered by a line in `CraftworksGameTests.registerTests`. The Assemblers' rings (`assembler_connections`) are generated by `python3 scripts/build-machine-models.py`; a model past three blocks must be a composite, since Minecraft refuses an element beyond -16..32 and no headless run loads a model (`ModelBoundsTest` checks). Data only the Mod's own runs load lives in `src/gametest/resources`, which never ships (libworks ADR 0004): `DevPacks` switches on `gametest_pack/` in the game tests and `dev_pack/` in the dev client, the datapacks that stand in for what a pack would add. Packs a test switches on itself, such as one per batch, go under `gametest_packs/<name>/`.

Vanilla's and NeoForge's own code is in `build/moddev/artifacts/minecraft-patched-*-sources.jar`, read with `unzip -p <jar> net/minecraft/.../X.java`. Check a claim about vanilla behaviour there before stating it.

Neither run loads a client, EMI, JEI or Jade, so a change to their compat code, a screen, or a model or texture isn't done when the tests pass: list it for the user to check in the dev client, which they open (the `quicklaunch` skill, only at their word). The dev client loads `dev_pack/` (`craftworks:dev/with_fluid`, `craftworks:dev/two_fluids`, `craftworks:dev/fluid_only`, `craftworks:dev/two_results`) for the cases vanilla's recipes don't cover; add a recipe there when a change needs one to be seen. EMI builds its recipes on a loading thread of its own: nothing in a plugin's registration or a recipe's constructor may touch the font or `RenderSystem`, which only the render thread may, or EMI drops the whole plugin (as #33's text measuring did).
