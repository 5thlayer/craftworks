# Craftworks

Factorio-style automated crafting: the Personal Assembler, a player-held crafting planner, and two placed machines on FE, the Assembler, which makes one held recipe over and over, and the Refiner, an electric furnace. See `GLOSSARY.md` for the domain glossary.

## Workflow

Commit on the current branch; open a feature branch only when the user asks for one. Nothing is pushed without the user's word. Asking a session to steward a PR is the user's word for that PR's pushes, its rebases onto `main`, and its merge, under the `steward` skill.

Anything that changes the Mod's behaviour gets a `/code-review`: the project skill in `.claude/skills/code-review`, from mattpocock/skills, never the built-in review of the same name. Doc and plumbing changes skip it: that covers `CLAUDE.md`, `GLOSSARY.md`, ADRs, `docs/`, `.claude/`, submodule bumps, and tooling or CI config.

## Commits

Conventional commits: `<type>(<optional scope>): <summary>`, with the summary in the imperative and lower case. The types in use are `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci` and `chore`. A breaking change marks its type with `!` (`feat!: ...`), and its release bumps the minor (libworks' ADR 0001). A commit that closes an issue ends its body with `Closes #<n>`.

## Testing

### Running the tests

- `sh ./gradlew build` runs the JUnit tests, on a plain JVM with no Minecraft: the Personal Assembler's planning.
- `sh ./gradlew runGameTestServer` runs the game tests headless, a real player on a real server with only Groundworks beside the Mod, and names each one it ran; it fails if it ran none.
- The `skillworks:gametest-loop` skill runs a subset, `--tests 'craftworks:<glob>' 1`, one glob a run, so a ticket's new game tests share a name prefix that selects them all.
- The libworks plugin's `checkPlaysAlone`, which `build` runs, fails on another Module's id, namespace or required dependency in the Mod's code or resources, its generated vanilla pack included (libworks ADR 0005).
- `PlaysAloneTest` fails on a tag the code reads that the game tests don't check, and `PlaysAloneTests` on a tag the Mod's data names that only another mod fills (FactoryWorks ADR-0127).
- The Assemblers' rings (`assembler_connections`) are generated by `python3 scripts/build-machine-models.py`.
- A model past three blocks must be a composite, since Minecraft refuses an element beyond -16..32 and no headless run loads a model (`ModelBoundsTest` checks).
- CI (`.github/workflows/ci.yml`) runs both through libworks' `module-ci.yml`, at the tag of the plugin `build.gradle` applies, on every push and never publishes.

### Game-test code

- Everything that exists only for the Mod's own runs lives in the `gametest` source set, which never ships (libworks ADRs 0004 and 0011): its game-test code, its test-only resources and its packs.
- `CraftworksGameTests` hooks itself in from `FMLConstructModEvent`, and `src/main` never names game-test code.
- Where shipped code must report to a test, `main` holds a hook with no test vocabulary that the game-test side fills.
- A new game test class is registered by a line in `CraftworksGameTests.registerTests`, and its tests stand on the `gametest/platform` structure that the plugin's `buildGametestStructures` task writes into `src/gametest/resources`.
- `DevPacks` switches on `gametest_pack/` in the game tests and `dev_pack/` in the dev client, the datapacks that stand in for what a pack would add.
- Packs a test switches on itself, such as one per batch, go under `gametest_packs/<name>/`.

### The dev client

- Pipeworks, Jade and EMI or JEI are on the dev client only.
- `-PwithKubeJS` puts KubeJS on both runs; `-PwithAE2` puts AE2 there, `-PwithCurios` puts Curios and Dark Utilities there, and `-PwithSophisticated` puts Sophisticated Backpacks there.
- Neither run loads a client, EMI, JEI or Jade, so a change to their compat code, a screen, or a model or texture isn't done when the tests pass: list it for the user to check in the dev client, which they open (the `quicklaunch` skill, only at their word).
- The `skillworks:quicklaunch` skill opens the dev client into the most recent save in `run/saves`, one client per checkout.
- The dev client loads `dev_pack/` (`craftworks:dev/with_fluid`, `craftworks:dev/two_fluids`, `craftworks:dev/fluid_only`, `craftworks:dev/two_results`) for the cases vanilla's recipes don't cover; add a recipe there when a change needs one to be seen.
- EMI builds its recipes on a loading thread of its own: nothing in a plugin's registration or a recipe's constructor may touch the font or `RenderSystem`, which only the render thread may, or EMI drops the whole plugin (as #33's text measuring did).

### Vanilla and NeoForge sources

- Vanilla's code, with NeoForge's patches, is in `build/moddev/artifacts/minecraft-patched-*-sources.jar`.
- NeoForge's own classes (`net/neoforged/...`) are in `~/.gradle/caches/modules-2/files-2.1/net.neoforged/neoforge/<version>/*/neoforge-<version>-sources.jar`, `<version>` being `neoforge_version` in `gradle.properties` (the cache keeps older ones).
- Read either with `unzip -p <jar> <path>/X.java`, and check a claim about vanilla or NeoForge behaviour there before stating it.

## Releases

A change a player or pack author notices adds its line under `## Unreleased` in `CHANGELOG.md` as it lands. Before bumping `mod_version`, publishing to `~/.m2`, tagging a release or uploading to Modrinth or CurseForge, read `docs/agents/releases.md`: releases go through the libworks plugin's `release` task, which uploads last with its `upload` task, and a published version never changes, in `~/.m2` or on either site.

A release that moves with Groundworks or Pipeworks follows the `release-train` skill: one owning session per checkout, and pushes only on the user's word.
